Rekayasa Perangkat Lunak (Software Engineering) Pengertian, Tujuan, Peran

Definisi RPL

  • Pendekatan terstruktur mengembangkan software (Dennis, 2012)
  • Representasi proses pengembangan software (Sommerville, 2015)
  • Serangkaian aktivitas & milestone untuk software berkualitas tinggi (Pressman, 2015)
  • Software = Kode Program + Dokumentasi

Kualitas Software (IEEE, 1991)

  • Degree to which system MEETS SPECIFIED REQUIREMENTS
  • Degree to which system meets CUSTOMER / USER NEEDS
  • Software Berkualitas = Sesuai Kebutuhan + Ada Business Value
  • Boehm's Law: Error paling mahal ditemukan di fase LATE

UML – Unified Modeling Language Standard Language Visualisasi, Spesifikasi & Dokumentasi Artifacts Software

Definisi & Prinsip UML

  • Unified Modeling Language – notasi pemodelan standar
  • Technology & language independent (tidak tergantung platform)
  • Alat komunikasi antar team & stakeholder
  • UML adalah NOTASI, bukan metodologi/proses pengembangan
  • Dibuat oleh Booch, Jacobson, Rumbaugh (3 Amigos, 1990an)

UML dalam SDLC (Wahono, 2009)

  • Analysis: Use Case Diagram → identifikasi proses bisnis
  • Analysis: Activity Diagram/BPMN → pemodelan proses
  • Analysis: Sequence Diagram → realisasi proses bisnis
  • Design: Class Diagram → struktur & relasi kelas
  • Design: UI Design, Data Model, Deployment Diagram

⚠️ Poin Penting & Common Mistakes yang Sering Keluar di Ujian

  • Use Case = apa yang dilakukan ACTOR di sistem (BUKAN apa yang sistem lakukan terhadap aktor)
  • Actor manusia hanya kirim message ke BOUNDARY CLASS (tidak ke Control atau Entity)
  • Entity Class BUKAN consumer: tidak pernah kirim message ke Boundary atau Control
  • Nama Object Lifeline, Class, Method TIDAK BOLEH pakai SPASI (akan jadi kode program)
  • Setiap Use Case → min. 1 Activity Diagram → min. 1 Sequence Diagram → class candidates
  • Boehm's Law: Error paling sering di fase Requirements & Design; makin terlambat makin mahal
  • Boundary → UI Design | Control → Business Logic | Entity → Data Model
  • <<include>> = selalu dipanggil (mandatory) | <<extend>> = opsional/kondisional
  • System Request: Business Need + Business Value (Tangible & Intangible) + Business Requirements
  • Feasibility Analysis: Technical + Economic (ROI, BEP, NPV) + Organizational
  • UML adalah NOTASI/bahasa, bukan metodologi atau proses pengembangan software
  • Class Diagram: menunjukkan STRUKTUR & KOMPOSISI, BUKAN alur (alur = Sequence Diagram)
